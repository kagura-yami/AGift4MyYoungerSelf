# Project Context Analysis

## Analysis Purpose

将 Tripothon 部署到 Windows / RTX 5060，网页通过 FRP 对外提供游玩，并保持部署目录可以迁移。

## Codebase Structure

- `game/Tripothon.uproject`：UE 5.7，启用 PixelStreaming2。
- `game/Config/DefaultGame.ini`：现有 Shipping 烘焙范围包括主菜单、Home、School 和 lv4。
- `tools/scripts/package_game.ps1`：Win64 BuildCookRun，支持 Shipping 和自定义输出目录。
- `tools/deploy/pixel-streaming/`：Compose、Dockerfile、配置生成器、启停和迁移脚本。

## Dependencies

运行游戏需要 Windows、NVIDIA 驱动和 UE 打包运行库。网页使用 UE5.7 对应的 Epic PixelStreamingInfrastructure，固定源码提交和 npm 锁文件。Docker Desktop 使用 Linux 容器。公网连接由已有 FRP 和独立 Coturn 完成。

## Connections

UE 游戏通过本机 WebSocket 8888 连接 Docker 信令；浏览器通过 HTTPS → FRP → 本机 8080 加入。视频、音频和输入使用 WebRTC，经公网 TURN 中继，不通过普通网页代理传输。

## Architecture Patterns

采用原生 GPU 游戏进程与容器化网页服务分离部署。单实例限制一个玩家，不实现多用户进程调度或账号存档隔离。

## Codebase Conventions

部署相关内容放在 tools 下，不增加仓库根目录服务配置。打包产物放在忽略的 artifacts 下，密钥和运行数据分别放在忽略的 runtime、Data 下。

## Dependency Graph

```text
Tripothon.uproject → PixelStreaming2 → NVIDIA H.264 编码
package_game.ps1 → Shipping Game/ → Start.ps1
Dockerfile → Epic UE5.7 → 网页/信令
Configure.ps1 → signalling.json + TURN 共享密钥
浏览器 → HTTPS/FRP → 信令 ← Windows 游戏
浏览器 ↔ 公网 Coturn ↔ Windows 游戏
```

## Component Relationships

Start.ps1 等待网页容器健康后启动打包 EXE，将 UE UserDir 指向部署目录的 Data/game；Stop.ps1 只停止该部署记录且身份匹配的游戏进程。Export.ps1 复制完整游戏和服务脚本，可导出 Docker 镜像供离线迁移。

## Key Insights

FRP 映射网页不能保证 WebRTC 穿透，公网模式需要可用 TURN。Windows 打包游戏运行在目标机原生环境，容器仅承载网页和信令。完整操作见 [部署说明](../tools/deploy/pixel-streaming/README.md)。公网服务器和目标机尚未提供远程访问，因此本机验证通过也不等于公网已上线。
